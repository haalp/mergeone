# Evidence, including what did not work

The long version of the README's scoreboard. Everything rests on **gatebench**, a pre-registered benchmark: hypotheses and thresholds were committed before any model ran ([PROTOCOL.md](../PROTOCOL.md)); every deviation is dated in [CHANGELOG.md](../CHANGELOG.md); results are published whichever way they fall. Short dated entries: [mergeone.dev/updates](https://mergeone.dev/updates/).

What survives: typed triage of *what a change does* at System One speed and cost, a gateway that handles 30 million decisions a day on a 2-vCPU box, a cheap model that can tell whether two PRs are *the same change* (0.83–0.87 AUC, ≤ $0.0005 per PR), and — run 6B — a hold for duplication that is right 98 times in 100, though more than half of the time the right action is a link, not a close; and — run 8, against a same-day control — a compact state that costs ≤ 0.02 AUC for 32–42 % fewer tokens, plus a drift monitor that replays run 7's drift exactly. What does not: predicting what a project will *accept* from one diff; finding the right PR to compare against; rewording the prompt or replacing the model with structure (run 7); and — runs 7 and 8 — a typed relation between two PRs beyond what the base branch already says (0.74 class accuracy, bar 0.80). Run 7's lasting result is that a hosted model's version string is not a pinned model. Details in [`results/`](../results/) and on [mergeone.dev](https://mergeone.dev).



## Run by run

**Run 1, negative.** *Can a cheap decision layer predict 30-day reverts from a pre-merge diff?* No. Rules, LightGBM, Claude Haiku 5.5 and Jev all land at PR-AUC ≈ 0.010 against a 0.0075 base rate, indistinguishable within CIs. That signal is not in the diff. We did not build a product on it.

**Run 2, positive.** *Can it answer rule-like questions that cannot be written as rules?* Yes. Against a Sonnet 5.5 judge (self-agreement 92–100%) on 1,200 PRs:

| question | Jev AUC | Haiku AUC | Jev ECE (cal.) | Haiku ECE (cal.) |
|---|---|---|---|---|
| is_logic_change | 0.94 | 0.95 | 0.030 | 0.027 |
| weakens_tests | 0.96 | 0.96 | 0.031 | 0.009 |
| message_matches_diff | **0.80** | 0.78 | 0.037 | 0.045 |
| touches_concurrency | 0.95 | 0.96 | 0.016 | 0.017 |
| needs_human_review | 0.87 | 0.88 | 0.047 | 0.041 |
| per PR, five questions | **347 ms · $0.074/1k** | 1067 ms · $0.314/1k | | |

Jev meets the pre-registered bar on 5/5 questions, Haiku on 4/5; asking five questions instead of one costs Jev 3% latency and 12% cost. What still fails: routing the top 25% to humans captures only 44% of the judge's "needs a human" PRs (bar was 70%). That number is in the README on purpose.

**Run 3, negative.** *Does the gate predict whether humans reject real agent PRs?* No. On 2,196 PRs by Copilot, Claude Code, Claude, Devin and Cursor across 26 public repos (held-out test: 705 PRs, 8 repos), calibrated `needs_human_review` → *closed-unmerged ∨ change-requested* scores ROC-AUC **0.55** for Jev, 0.55 for Haiku, 0.53 for rules; the pre-registered bar was 0.70. The reason is in the labels: of 200 closures we classified, 67% were *superseded, duplicate or direction* and only 19% *quality*. A diff cannot tell you someone else already landed the fix. Two things did hold: Jev at 100× agent-scale load — p99 417 ms, 0 errors (Haiku: 2,880 ms, 0.3% errors) — and, exploratory only, the questions track *review iteration* (force-pushes ≥ 2) at AUC 0.70–0.81. Full write-up: [`results/run3/README.md`](../results/run3/README.md).

**Run 4, mixed.** *Can a per-repository PR memory catch the duplicates run 3 found?* Half of it. Given a candidate pair, the typed question `same_change(A, B)` separates maintainer-confirmed supersedes from the rest at ROC-AUC **0.87** (Perplexity pplx-decider, open weights), **0.84** (pplx-flash, 4B) and **0.83** (Jev) on 187 held-out pairs — all above the 0.80 bar, all at ≤ 0.5 s p99 and ≤ $0.0005 per PR; Claude Haiku 5.5 scores 0.76 and fails. But the deterministic retrieval that picks the candidates finds only 55% of the gold duplicates in its top 5 (bar 0.60), so at the verdict level the dedup rule lowers the pass group's bad-outcome rate from 0.41 to 0.36 (bar: 0.23) and catches 8 more points of closed PRs (bar: 15). Retrieval p99 is 198 ms against a 20 ms bar. Four of five hypotheses fail; the one that passes is the one that was uncertain. Memory ships opt-in. Full write-up: [`results/run4/README.md`](../results/run4/README.md).

**Run 5, mixed.** *Can the gate be made better on the two things runs 3–4 exposed — finding the PR to compare against, and knowing which PRs will need review?* Partly. Retrieval v2 (shared-issue references, directory overlap, weights fit on val only) lifts recall@5 from 0.55 to **0.66** — short of the 0.70 bar, and the changed-line content stage moved nothing — while the Go store answers in **3.3 ms p99** against a 20 ms bar. Run 3's exploratory finding becomes a result: calibrated `needs_human_review` predicts ≥ 2 force-push rounds at AUC **0.76** for Jev and for the 4B open-weight pplx-flash (bar 0.70); the ten-question stack misses its 0.75 bar for every System One model because the val-chosen pruning rule dropped `hard_to_revert`, the strongest question on test (0.85). Declared assumptions could not be judged — maintainers wrote a numbered "depends on / conflicts with" comment on 9 of 2,196 PRs. Both Perplexity models hold p99 flat from 1× to 100× and then lose 71% of calls to HTTP 429: a per-org rate limit, which self-hosting the open weights removes. Full write-up: [`results/run5/README.md`](../results/run5/README.md).

**Run 6A, negative.** *Do the open weights clear the scale bar when we serve them ourselves?* Not on one GPU. pplx-decider-flash-v1.2 on a rented NVIDIA L4 ($0.59/h), served with the vendor's own code, agrees with the hosted endpoint on **95.2%** of answers but not within the 0.02 mean |Δp| bar (0.047), so it counts as a different model; its quality is a CI-width away (AUC **0.747** vs 0.758, pair task 0.840 vs 0.842), one-question-per-request gains **+0.000** AUC for 10× the calls (joint stays), and the server saturates at **~2.2 requests/s** — 6× the base rate, with ×10 already queueing and ×100 losing every call. The vendor's rate limit becomes a capacity-planning problem; one 24 GB card is an order of magnitude under the target. $1.44 of GPU; a second pass on an H100 ($4) found the only lever is a faster card (30× at 160 ms p99, 100× fails; batching flat). Full write-up: [`results/run6/README.md`](../results/run6/README.md).

**Run 6B, positive.** *When the gate holds a PR as a duplicate, is it right?* Yes. Of 100 PRs that pplx-flash holds at `duplicate_of ≥ 0.7` with a 20-candidate pool (stratified, blind, labelled by the author over five days with the taxonomy written down at item 35), **98** were right to hold — dup ∪ pointer **0.98** [0.93, 0.99] against a 0.60 bar — and **44** are the same change (bar 0.30). The other 54 are *pointers*: the held PR's author should have looked at the candidate first — backports and edge→stable promotes (≈ 28), competing fixes (≈ 8), follow-ups and repro↔fix pairs (≈ 6), reverts (2), same area (≈ 10). When the held PR was later merged, six in seven holds are pointers; when it was closed without a label, three in four are the same change. A second blind labeller (Fable 5.1, not pre-registered) agrees at κ **0.77**, differing only on where duplicate ends and pointer begins; the 12 disagreements are adjudicated in a separate file (46 / 52 / 2). The pool size is not the lever (R6B-H1 ❌: the pass-group bad-outcome bar fails at every k; k = 10 is the default) and k = 20 costs $0.0004 per PR (R6B-H3 ✅). Consequence: the dedup rule stays a hold, a hold never closes a PR (at 0.9 still 40% pointers), and the next question is the *relation* between two PRs, not just whether they are the same. Full write-up: [`results/run6/README.md`](../results/run6/README.md), tables [`results/run6/b_tables.md`](../results/run6/b_tables.md).

**Run 7, negative four times.** *Compact state, prompt tuning, a structural evidence floor, a typed relation question.* All four pre-registered bars fail. Compact rendering (diff 2,000 chars, body 600, 20 files) scores −0.049 mean v3 AUC against run 5's full-state number on pplx-flash (R7-H1 ❌; jev −0.002); the tuned prompt, frozen at round 2 of a possible five after one rejected round, scores −0.059 against run 5's untuned number (R7-H2 ❌); seven structural features fit on val score 0.484 on test and subtract 0.10–0.17 when stacked on `needs_human_review` (R7-H3 ❌); the four-binary relation question reaches 0.73 / 0.69 same-change AUC against a 0.80 bar, +0.03 / +0.01 over the single pair question (R7-H5 ❌). The finding that outlives the verdicts: run 5 and run 7 asked `pplx-decider-flash-v1.2` the same prompt on the same 1,491 val PRs five days apart and two questions came back different — `follows_conventions` mean probability 0.26 → 0.82, `message_matches_diff` 0.67 → 0.93 — and Jev moved 1.13.0 → 1.14.0. Same-day full-state controls, made after the verdicts and labelled post-hoc, put compact at +0.014 / +0.007 and the pair at −0.015 (inside the bar) and tuning at −0.008 (nothing gained); the verdicts stand as pre-registered. The relation question's class accuracy (0.08 / 0.32) is the model being asked for a fact the gateway has: substituting the metadata base branch for its `same_branch` answer gives 0.72 for both models, backport 27/28. Consequences: nothing ships from run 7; run 8 pre-registers a same-day control for every cross-run comparison and asks the relation question only about what the diff can answer. Write-up: [`results/run7/README.md`](../results/run7/README.md), tables [`results/run7/tables.md`](../results/run7/tables.md), dated deviations in CHANGELOG.md "Run 7 complete".

**Run 8, two passes, one fail.** *Asked fairly — every comparison against a same-day control in the same directory — does compact state hold, does a three-question relation prompt split the pair classes, and would the drift monitor have caught run 7?* Compact state passes (R8-H1 ✅): against the full state rendered the same day by the same model, the compact rendering scores **+0.010** (Jev) and **−0.001** (pplx-flash) mean AUC on the eight v4 questions and **−0.018 / −0.015** on the pair question over 187 eval pairs, all inside the −0.02 bar — the pair deltas sit on it (Jev's CI [−0.035, −0.004] excludes zero) — for 32 % to 42 % fewer tokens per request. The run-7 fail was the comparison, not the rendering. Relation v2 fails (R8-H2 ❌): `same_change`, `builds_on`, `same_goal` plus the metadata base branch reach class accuracy **0.740** (Jev, exactly its baseline) and **0.570** (pplx-flash, down from 0.722; its `builds_on` over-fires) against a 0.80 bar; competing + same-area **3/17** and **1/17** against 0.40. The same-day control (run 7's question asked today, 0.747 / 0.720) says this is the prompt, not the day. v4, the v3 set minus the two drifted questions, equals its control on the eight that stay (+0.001 / +0.000; R8-H3, no bar). The C4 self-hosted row is deferred again (no candidate licence named by freeze). The drift monitor passes (R8-H5 ✅): `mergeone drift-replay`, the gateway's own Go path, flags exactly `follows_conventions` and `message_matches_diff` for pplx-flash run 5 → 7 (val and test), nothing on Jev or on the run-6A self-hosted row, no false positive; the slow signal (Python reference) flags Jev `tests_cover_change`. Post-hoc, beside run 7's verdicts and not in place of them: the research note [`docs/research/inference.md`](research/inference.md) finds the hosted run-7 answers match our self-hosted one-question-per-request rows (agreement 0.990, mean |Δp| 0.014) and their token count — more likely a request-handling change at the provider than new weights; pre-registered for run 9 as R9-H5. Consequences (gateway v0.3): compact state becomes the pair-call default, the v4/v3 call keeps the full state; `drift.enabled` defaults to true; `duplicate_of` stays the only edge. Perplexity ≈ $0.40. Write-up: [`results/run8/README.md`](../results/run8/README.md), tables [`results/run8/tables.md`](../results/run8/tables.md), dated deviations in CHANGELOG.md "Run 8 complete".

The ordering is decided by the scale column, not by a few AUC points. Haiku matches Jev on quality and fails the 100× bar in every run on latency. The two Perplexity models lead on quality in runs 4–5 and hold their p99 flat from 1× to 100× — and then lose 71% of calls to the hosted API's 10 rps per-organisation limit (run 5). That is a vendor ceiling, not a model one: the same weights self-hosted (a `provider:` row pointing at llama.cpp or vLLM) carry no such limit — and run 6A measured it: on one L4 the limit becomes throughput (~2.2 requests/s, saturating at ×10), at 20× the hosted list price per PR. Quality is not comparable across runs (different tasks), so a mean over runs is a tie-breaker, not a score. The remaining open-weight candidates (Cloudflare `clef`, AutoTrust `JEV-9B/27B`, H2O Lightning 4B, Laya 421M) are in the registry; until they have a row, their public-leaderboard numbers are claims, not measurements.

**Any model, one YAML row.** The gateway does not know the model's name. [`prompts/models.yaml`](../prompts/models.yaml) lists each candidate once — wire dialect (`systemone`, `decide`, `anthropic`), endpoint, key variable, model id, list price — and `model: <row>` in `.mergeone.yaml` or `--model <row>` in gatebench uses it. A private llama.cpp or vLLM server serving open weights is a `provider:` block in the policy; no code, no rebuild. `mergeone models` prints the registry.
